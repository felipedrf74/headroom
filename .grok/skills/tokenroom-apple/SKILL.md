# Tokenroom for iPhone and Apple Watch

The Mac collects; everything else reads. Macs relay readings through the user's private CloudKit database. The iPhone adds providers it reads with its own API keys. The Watch reads iCloud directly. There is no Tokenroom server. Mac rules (providers, tokens, the menu bar) are in `.grok/skills/tokenroom-macos/SKILL.md`.

## Targets and folders

| Target | Bundle ID | Compiles |
|---|---|---|
| TokenroomMobile (iOS 26) | `app.tokenroom.ios` | `TokenroomMobile/`, Shared Core, Relay, UI, APIKeys, Widgets |
| TokenroomWidgets | `…ios.widgets` | `TokenroomWidgets/`, Shared Core, Relay, UI, APIKeys, Widgets |
| TokenroomWatch (watchOS 26) | `…ios.watchkitapp` | `TokenroomWatch/`, Shared Core, Relay, UI |
| TokenroomWatchWidgets | `…ios.watchkitapp.widgets` | `TokenroomWatchWidgets/`, Shared Core, Relay, UI |
| TokenroomMobileTests | `…ios.tests` | `TokenroomMobileTests/`, hosted in the app |

Folders are Xcode synchronized groups: a new file in a folder joins every target that uses the folder. `Shared/Widgets` is iPhone-only (app and widgets). The Watch never compiles `Shared/APIKeys`: no keys on the Watch. Widgets and both Watch targets build with `TOKENROOM_RELAY_READONLY`, which leaves `CloudRelay`'s write methods out. The app embeds the widgets (Embed Foundation Extensions) and the Watch app (Embed Watch Content, `$(CONTENTS_FOLDER_PATH)/Watch`). The Watch app embeds its complications.

Settings live in `Config/*.xcconfig` (`Mobile`, `Widgets`, `Watch`, `WatchWidgets`); never add build settings or `DEVELOPMENT_TEAM` to `project.pbxproj`. Info.plist values that must be filled in by the build (`TokenroomCloudContainer`, `TokenroomAppGroup`, `TokenroomKeychainGroup`) are read through `RelayAvailability` and `AppGroup`, which return nil when a build left them empty. A build without a container (no team) runs without iCloud: the iPhone says "This build can't use iCloud" and still reads keys and offers sample data, and the Watch shows sample data. (The plan had such a build show only sample data.)

`./scripts/typecheck-shared.sh` checks Shared for macOS, iOS, and watchOS (`Shared/Widgets` for iOS only). Run it after touching Shared.

## Data

- **Relay** (`Shared/Relay/CloudRelay.swift`), zone `Tokenroom`: `Source` (one per collector, one writer each), `History` (`hist-<source>`), `Event` (alerts, with `alertKey`; an alert the iPhone shows itself is first claimed with `claimAlert`, created only if no device has, under `UsageAlert.shownKey` so no subscription sends it back), `Prefs` (`prefs-alerts`, the alert choices, written by the iPhone and Macs through `AlertPreferencesSync`: each device keeps the copy it last knew matched iCloud and lays its own changes over the newest shared copy, field by field and threshold level by level, so neither undoes the other; fields a newer Tokenroom added are kept. A copy sent is dated no earlier than the ones it builds on. The iPhone shares one round at a time, and a change made while one goes out follows in the next, laid over what went out; it skips the choices in a zone read that began before its last share reached iCloud (`preferencesSharedAt`), which may hold the copy from before, and doesn't adopt while a share is going out. The record is saved without a change tag, so a change another device saves between this one's read and its save is lost). Macs only create alert records (`saveAlert`); an existing one, a claim included, is left as it is. The iPhone, and Macs while sync is on, delete alert records older than two weeks, in batches of at most 400. Envelope windows may carry `pace` (the Mac's measured run-out, which `Pace.evaluate(measured:)` prefers) and providers a `category`. `RelayErrorPolicy` maps CloudKit errors for the Mac and the iPhone alike. Records hold readings only: never tokens, keys, emails, names, account or organization IDs, or paths. `MobileLogicTests.testNoKeyMaterialReachesAnyRecord` guards this. Payloads are plain fields, not `encryptedValues`, by choice: they hold nothing beyond usage numbers, provider and plan names, and reset times; encrypted fields are lost if the account's encryption keys are reset and can't be queried; and with Advanced Data Protection on, the private database is end-to-end encrypted anyway. Moving to encrypted fields later means a new field and a `minReader` bump.
- **Merging**: `RelayMerge` picks each provider's reading (live beats stale, then newest). `ReadingAssembler` adds each collector's history and ranks by urgency (`UsageRanking`: limit reached, running out, most used; balances last). The app, iPhone widgets, the Watch, and complications all go through it.
- **iPhone as a collector**: providers read with keys on the iPhone are relayed as its own `Source` (`kind` `iphone`), with `RelayPublishPolicy`'s send rules. Each of the iPhone's providers shows its newest reading: this launch's, or its own iCloud record's or the App Group cache's (widgets write there too), up to a week old, so a silent-push launch (which doesn't read keys) or a provider resting between calls never drops out, reads "loading", or goes back in time; a key that stopped working shows as that, and when this launch's check failed (offline, busy, rate limited) after the stand-in's reading was taken, the stand-in takes that failure's state, so it's faded and not relayed as live (one a widget took after the failure shows as it is). Until a launch has read iCloud, the saved cache's readings from other devices stand in too (`ReadingCache.carriedSources`, as in widgets), so a launch that can't reach it doesn't show only this iPhone's; signed out of iCloud (`.noAccount`) counts as an empty read, and the next account starts afresh (choices base, subscriptions, publish state). Every iCloud call in a refresh answers within 20 seconds (`MobileStore.iCloud`, over `TimeLimit`), so one that never answers can't hold that refresh, or the ones queued behind it. Budgets and references apply when readings are shown, so changing one shows at once, on saved readings too: a limit that's a budget is marked (`QuotaAmount.isBudget`), and `RelayProvider.applyingBudget` measures it again. The list of providers with keys is saved (`keyedProviders`), and the iPhone doesn't publish until the launch has read its keys; saving or removing a key publishes on that refresh and clears its spacing and 429 wait (`KeyFetchGate.reset`; each value is a defaults key of its own, so one provider's never overwrites another's, though the same provider's is last-writer-wins and checking then recording isn't atomic across the app and widgets). Coming back to the app (and launching it) refreshes a minute after the last refresh that read keys, stamped when a refresh starts and taken back if it's cut short (a silent push in between doesn't count); a refresh asked for during another, forced or due, gets one more pass after it, in a task of its own, so a push's deadline doesn't cut it short. A silent push refreshes readings only (no keys, subscriptions, or pruning), answers within 25 seconds whatever iCloud does (`TimeLimit`, which then cancels it), and tells iOS whether anything changed; background refresh asks for the next one first. Quiet hours take this iPhone's time zone only when that zone changes (`followedTimeZone`), so two iPhones in different zones don't take turns rewriting it. `MobileAppDelegate` owns `MobileStore` and `NewsStore`, so background launches have them. Keys stay in the Keychain group `TEAMID.app.tokenroom.shared`, `AfterFirstUnlockThisDeviceOnly`, never synchronized.
- **Cache**: `ReadingCache` (`readings.json`) in the App Group. The app rewrites it on each rebuild but reloads widgets and hands it to the Watch (WatchConnectivity) only when its `materialHash` changes (amounts count as shown, cents for money; run-outs don't count: `RelayPublishPolicy` sends one once it moves an hour from the one last sent, widgets don't draw them, and the Watch, which does, is handed a run-out that moved an hour too). From the background, where reloads count against WidgetKit's budget, it reloads widgets only for what matters (`ReadingCache.reloadSignature`: a provider added or gone, its state, a level crossed at 80%, 95%, or used up, a window starting over), measured from the saved cache at launch; a reload held back goes out when the app comes forward (anything but `.background` counts as forward). The Watch reloads complications the same way. Sample caches never go to the Watch, and when this launch hasn't sent any readings the Watch link hands over the saved ones. The Watch takes its own iCloud read or the iPhone's handover unless it holds an older reading of a provider shown (`ReadingCache.isAtLeastAsFresh`), not by when it was saved; a provider gone from it doesn't hold it back.
- **Widgets and complications** read the cache; when it's over 15 minutes old they read iCloud (and the iPhone's keys, on iPhone) for at most 6 seconds. They never write to iCloud. Widgets due together share one refresh per process (`WidgetRefresher`). `KeyFetchGate` (App Group) shares key-call spacing and 429 waits between the app and widgets. Timelines add an entry at each reset in the next 8 hours (`rolledOver(at:)`) and ask for the next one through `WidgetSchedule`: every 30 minutes while a live window is at 80% or more and resets within 12 hours, hourly otherwise, and hourly once that widget has reloaded 32 times in 24 hours, so even a busy day stays within about 40. iCloud and each key provider get at most 5 of the widget's 6 seconds (`TimeLimit`, `fetchWithinBudget`), hard limits that don't wait for a call that ignores cancellation; when iCloud doesn't answer in time, the previous cache's readings from other devices stay beside the fresh key readings. Countdowns use `ResetCountdown` (a ticking timer within a day). "Updated … ago" dates from the freshest reading's check (`ReadingCache.checkedAt`), so one fresh key reading can make older Mac readings look current. `WidgetReloadLog` counts each widget's timeline builds (family and chosen provider); Settings › About shows the busiest widget's last 24 hours (aim: under 40). Accessory families say "Sample" for sample data, and a balance shows its amount rather than an empty gauge (circular and, on the Watch, corner and rectangular). Outside debug builds a sample cache ages like any other. Circular and corner complications open their provider; rectangular and inline ones open the list. The Smart Stack offers both the last 8 hours before the followed window resets and the next half day of the busiest window at 80% or more (`WidgetSchedule.relevance`).
- **History** (`UsageHistory`): 168 hourly used-% buckets, plus the hourly amount left for balances and the reset times, all optional in older records. Resets include ones used early (use falls sharply, to 10% or less, once the new window has begun). `HistoryStore` leaves out readings dated over an hour ahead, restarts a week that ran ahead of the clock, drops windows with no reading for a week, and moves Copilot's 2.0.0 `ai_credits` week to `premium_interactions`. Widgets queue the key readings they take (`history-pending/`, a file per provider and hour holding its latest reading, dropped after a week) for the app to record on its next refresh, the app being the one writer of `history.json`, and show them meanwhile (`HistoryStore.loadWithPending`). The app moves them aside (`history-taking/`) before recording them and deletes them once the week is saved, so one queued meanwhile, or a refresh cut short, loses nothing. `Forecast` turns history into "≈ N days left" (a rise under 1%, or under one whole unit, isn't a top-up) and a projected month, measured to the reading's check time and not once the month is over or the reading is a day old.

## iCloud environments

The container is `iCloud.app.tokenroom` (`TOKENROOM_CK_CONTAINER` in `Config/Base.xcconfig`), zone `Tokenroom`. Builds Xcode installs (development signing) use CloudKit's Development environment; TestFlight, the App Store, and the Developer ID Mac release use Production (`scripts/release.sh` refuses an export without it). Devices see each other only within one environment, so pair them deliberately: an Xcode-built Mac with an iPhone and Watch installed from Xcode, and the notarized Mac with TestFlight or App Store builds.

Development builds create record types and fields as they save them. Anything new has to be deployed to Production in CloudKit Console (the container's Schema › Deploy Schema Changes) before a Production build uses it; otherwise its saves fail there. The schema:

| Record type | Records | Fields |
|---|---|---|
| `Source` | one per collector, named by its source ID | `payload` (a `RelayEnvelope`), `kind`, `label`, `checkedAt`, `schema`, `appVersion` |
| `History` | `hist-<source>` | `payload`, `schema` |
| `Event` | one per alert, `evt-…` | `provider`, `level`, `title`, `body`, `resetsAt`, `alertKind`, `alertKey` (queryable: the alert subscription filters on it) |
| `Prefs` | `prefs-alerts` | `payload` |

New data goes inside a `payload` (versioned JSON) rather than into new fields where it can, so it needs no deployment: 2.0.1 added none. The iPhone saves two subscriptions: one on the zone (silent pushes) and one on `Event` creation (visible alerts).

## Alerts

`AlertRules` and `AlertLedger` (`Shared/Core/Alerts.swift`). IDs are deterministic (`evt-<provider>-<window>-<level>-<instance>`: the reset rounded to the hour for windows a day or longer, 10 minutes otherwise, and the day for windows with no reset), so any number of devices seeing one crossing leave one `Event`; the iPhone's `CKQuerySubscription` fires only on creation and filters on `alertKey IN subscribedKeys` (falling back to every event if the field isn't queryable yet). First sight and stale readings never alert. A reset time that moves while the window goes on (the old time still ahead, the move no more than a quarter of the window or 30 minutes, use not falling by 10 points) is the same window, and "fresh headroom" is only for resets in the last 12 hours. Money windows (usd, cny) raise `.lowBalance` instead of `.threshold`, at 80% and 95% whenever the balance switch is on, whatever the usage levels; a balance alert, named by the day (UTC), first checks for either neighbouring day's record under a day old (`wentOutOnANeighbouringDay`), so two devices either side of midnight don't both alert, whichever goes first (a real second crossing within a day, after a top-up, is quiet). `process` queues alerts in `pending`; `due` releases urgent ones at once and the rest after quiet hours; `markSent` only after delivery, so an alert iCloud didn't take is retried. A held alert goes out with its countdown as of then (`AlertRules.refreshed`), is dropped when its switch is turned off or the same window's higher level went out (`levelsSent`, even when the reset moved between them), and waits through quiet hours of any length. Quiet hours and choices are shared as `Prefs`; the iPhone applies quiet hours where it is now and gives the shared copy its zone when that changes, so a Mac holds alerts for the same night. Urgent alerts (95%, a banked reset expiring within 6 hours) ignore quiet hours. The alert subscription sets no `collapseIDKey`: CloudKit would send it as every push's collapse ID. Macs send alerts; the iPhone notifies locally only for windows no Mac meters live (a reference set only on the iPhone makes that window its own), because iCloud doesn't notify the device that saved a record. Before notifying, the iPhone claims the alert (`CloudRelay.claimAlert`: creates the record only if no device has, keyed `UsageAlert.shownKey`, which no subscription lists). If a Mac's record is already there, its push already came and the iPhone stays quiet; another iPhone's (a `shown:` key) means nothing reached this one, so it shows the alert too. A Mac saving the same crossing later finds the record there and leaves it, which notifies nobody. Claims start once the alert subscription filters by kind. An alert shown while iCloud was away is claimed later (`unclaimedAlerts`, up to 18 hours). The ledger processes every provider the iPhone reads, so it stays current; only alerts for windows no Mac meters live (other iPhones don't count; Copilot's `ai_credits` from a Mac on 2.0.0 counts as `premium_interactions`) are shown here, the rest stay pending. The subscription falls back to every event only when CloudKit rejects the `alertKey` predicate (`invalidArguments`, `serverRejectedRequest`); other failures are retried on the next refresh. Add fields to `AlertPreferences` with a default in its lenient `init(from:)`.

## Live Activity

`SessionActivityAttributes` follows one window: a session, or a window at 80%+, resetting within 8 hours (`RelayProvider.windowToFollow`). Started from the Next up card, a row's swipe or context menu, the detail screen (`FollowButton`), `FollowUsageIntent` (Shortcuts, Siri via `TokenroomShortcuts`, Action button), or the Control. The app updates it on each rebuild (a refresh waits for that), alerting at 80% and 95% when those alerts are on (95% only during quiet hours); `staleDate` is the reset; it ends once the reset has passed, even without a newer reading, stale activities included. A stale activity shows as reset rather than at its last percentage and doesn't count as followed; following again ends it, and one still lingering after it ended, before starting the new one (`start` is async, so an intent doesn't return first, and runs on the main actor, checking again just before it starts one, so two Follows at once start one). A reset time the provider moves, with the window going on, updates it rather than ending it, even when the move is seen after the old time. Follow on the Next up card follows the window the card shows when it resets within 8 hours. `.supplementalActivityFamilies([.small])` puts it in the Watch Smart Stack.

## Checking UI without taps

Debug builds take launch arguments (they land in the standard defaults' argument domain):

- `-sampleMode YES -onboarded YES`: sample data, no onboarding.
- `-TokenroomOpen tokenroom://provider/claude` (or `news`, `settings`, `keys`): open a screen.
- `-TokenroomGallery home` or `lock`: every widget size and the Live Activity's Lock Screen view.
- `-TokenroomFollow claude`: start that provider's Live Activity.
- `-newsSection Models|Announcements`.
- Watch: `-sampleMode YES` and `-TokenroomOpen tokenroom://provider/claude`.

Build to a fixed DerivedData path so `simctl install` gets the fresh app, then `xcrun simctl launch <device> app.tokenroom.ios -sampleMode YES …` and `xcrun simctl io <device> screenshot`. Opening a URL with `simctl openurl` leaves an "Open in Tokenroom?" prompt; use `-TokenroomOpen` instead. Simulator screenshots don't show the Dynamic Island or Lock Screen, and `BGTaskScheduler` isn't available in the simulator.

## Copy and design

The Usage tab leads with Next up (the most pressing live metered window: `UsageRing`, pace, a live countdown, Follow) and highlight chips (banked resets, unseen models and updates from `NewsStore`, alerts off). Rows carry a 7-day `Sparkline` and a banked badge. The News tab badges unseen items and marks them "New" for the visit (`markSeen`). Feeds are read up to their size cap as they download (2 MB, and 4 MB for the ChatGPT & Codex changelog, whose items carry whole release notes); one cut short or broken shows what arrived, and its section says "Couldn't read …"; a failed check waits an hour. Titles fold into one row only within a product's own feeds (a changelog and its GitHub releases); across products only the same link does. Feeds and labs added since a list was saved start on. The first check (turning News on) marks nothing new, items are dated no later than first seen, and links are web pages only. Monograms and tints, never provider logos, on iPhone and Watch. Say "Tokenroom isn't affiliated with…" where a provider is named at length. Errors start with "Couldn't…". Links inside `List` and widgets tint their labels: set `.foregroundStyle(.primary)` on the `Link`.

App icons (a "T" of two usage meters, white on orange) are generated: `scripts/make-icons.py` writes `TokenroomMobile/AppIcon.icon` and `TokenroomWatch/AppIcon.icon` (a smaller T, so it clears the round mask). Change the script and rerun it; don't edit the `.icon` files by hand. Check a change in every look with Icon Composer's renderer: `ictool <file>.icon --export-image --output-file out.png --platform iOS --rendition Dark --width 512 --height 512 --scale 1` (renditions Default, Dark, TintedLight, TintedDark, ClearLight, ClearDark; platforms iOS, macOS, watchOS).
